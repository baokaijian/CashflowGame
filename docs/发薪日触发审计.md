## 二、触发条件：到达 vs 经过

### 2.1 代码依据

```js
function pathBetween(from, to){        // engine.js
  const out = []; let i = from;
  do{ i = (i+1) % RING_LEN; out.push(i); } while(i !== to && guard < 60);
  return out;                          // ← 末元素就是落点
}
```

`pathBetween` 生成的是**半开区间 `(from, to]`**：包含落点、不含起点。
`movePlayer` 对 `path` 整体遍历，逐格判断格型，因此

- **落在发薪日上** → 落点被包含在路径里 → 触发 ✅
- **只是经过** → 中间格被包含在路径里 → 触发 ✅

两种情形共用同一段代码，不存在「只处理其中一种」的分支。穷举验证：
24 × 18 = **432 种走法中，路径末元素全部等于落点**，无一例外。

### 2.2 实测（单人 101 · 种子 20260920 · 45 轮）

```
45 次移动，路径命中发薪日 20 次
  其中【到达】触发 8 次、【仅经过】触发 11 次、一次经过多个 1 次
```

> 8 + 11 = 19 个「有命中的回合」，而命中总数是 20 —— 差的 1 次来自那个「一回合经过 2 个发薪日」的回合。两个数字都能对上，没有第四种情况。

## 三、是否重复 / 是否遗漏

### 3.1 不重复 ✅

`movePlayer` 只做结算，`resolveSpace` 对发薪日格**只弹提示、不再入账**。实测：

| 检查 | 结果 |
|---|---|
| 落在发薪日的现金变化 | `¥25,080`，与引擎 `collected` 完全一致（不翻倍） |
| 该回合摊还期数 | 4 笔在贷负债**每笔**各 +12 期（一年），无一笔被重复摊还 |
| 落格弹层类型 | `info`（纯提示），不产生第二次入账 |

### 3.2 不遗漏 ✅（除暂停回合，见 §5.1）

- 长局 45 次移动中「路径命中数 === 结算记录数」（20 vs 20），不一致 0 次
- 遍历全部 `pending` 分支（入不敷出 / 机会 / 慈善 / 意外支出 / 失业 / 休假…）后仍成立
- **入不敷出路径不丢信息**：结算摘要挂在 `landed.settled` 上，一路穿过「入不敷出」面板并在补款后重新落格时仍存在

> 这一条是上一轮埋下的隐患：`landed` 在入不敷出流程里被 `Object.assign({}, landed, {deficit:0})` 复制，
> 若摘要挂在别处（如球员对象或全局）就会在重入时丢失，弹层会显示 ¥0。

## 四、年龄递增时机（核心问题）

> **后续更新**：本节记录的「两个时钟不同步」在审计后已由**方案 A** 解决
> （结算「自上次结算以来经过的年数」，覆盖率 44.4% → 93—100%）。
> 下面保留的是**审计当时**的实测与推导，它也是方案 A 的决策依据。

### 4.1 现状（审计当时）

```js
function ageOf(g){ return g.startAge + (g.round - 1); }        // 年龄 = 20 + 轮次 − 1
function nextPlayer(g){
  if(g.cur === 0){ trackRound(g); g.round++; refreshAllLife(g); ... }   // ← 整圈走完才 +1
}
```

**年龄的推进时机是正确的**（实测 45 轮推进 45 次；移动与发薪结算过程中年龄越界 0 次）。
问题不在时机，而在**它和发薪日是两个互不相干的时钟**：

| 时钟 | 由什么驱动 | 频率 | 覆盖 |
|---|---|---|---|
| **年龄时钟** | 整圈走完（`g.round`） | 每轮 1 次 | 45 轮 = 45 年 ✅ |
| **金钱时钟** | 落在/经过发薪日 | 内圈每轮 **0.438** 次 | 一生 45 年只结算 **20 年** ❌ |

内圈 24 格只有 3 个发薪日（位置 2/7/14），而每轮平均只走 3.5 格 ——
平均要 **6.9 轮才走完一圈**，一生 45 轮只能绕 6.5 圈。实测结果：

```
一生 45 年：年龄推进 45 次、发薪结算 19 次（合计 20 年）
→ 结算覆盖率 44.4%
发薪时刻的年龄：21, 24, 28, 30, 31, 34, 35, 37, 39, 40, 44, 47, 48, 51, 54, 57, 59, 62, 64
→ 两次结算之间平均间隔 2.25 年
```

### 4.2 为什么不能「让发薪日推进年龄」

这是这次要求的核心诉求，但**不能这么做**，原因有数：

1. 一生只有约 **19—20 次**发薪（上表）。若由它推进年龄，45 轮结束时角色只有 **39 岁**，
   「65 岁退休结算」这个胜负条件会立刻失效。
2. 要把发薪次数提到 45 次，内圈需要约 **7 个发薪日（29% 的格子）** ——
   棋盘只能从 8 个投资机会格里去砍，等于把核心玩法砍掉一半。
3. 更糟的是**激励会反过来**：谁更常踩到发薪日谁老得更快，
   于是「躲开发薪日」变成最优策略 —— 与实际直觉完全相反。

**结论：年龄时钟必须由「一轮 = 一年」独占。** 要消除两套时钟，只能让**金钱时钟去跟随年龄时钟**。

### 4.3 两条彻底对齐的路径（方案 A 已落地，B 为备选）

| 方案 | 做法 | 一生累计结算 | 代价 |
|---|---|---|---|
| **A（推荐）· 已实施** | 发薪日结算「自上次结算以来经过的年数」，而不是固定 1 年 | 45 年 | 单次金额变成 1—4 年不等；总收入约 **×2.25** |
| **B** | 每轮边界自动结算一年，发薪日改为一次性奖励 | 45 年 | 失去「踩到发薪日」的节奏感；棋盘上 3 个发薪日格失去意义 |

两方案的共同影响：**出圈条件（被动收入 > 总支出）是比率条件，不受影响**；
但累计现金会变成 2.25 倍，而资产价格是绝对值 —— 所以**中后期的购买力会明显上升，需要重新做一轮价格标定**。
在价格标定之前贸然切换会让游戏变得过于宽松，因此审计当时**未实施**，等决策。

> **后续更新**：方案 A 已实施，并配套一轮 **×2.15** 的价格标定（只换价格、不动收益）。
> 实测覆盖率 **93.3%—100%**（多数局 95%+），残差 0—3 年为「最后一次结算到退休」的尾巴，刻意保留。
> 完整推导与实测见 [`方案A与价格标定.md`](方案A与价格标定.md)。

## 五、边界情况与逻辑缺陷清单

### 5.1 ⚠️ 暂停回合：时间在走、账不走

失业休养与健康危机的 `skipTurns` 回合，玩家**不移动 → 不结算收入、也不摊还负债**，
但年龄照常 +1（实测：期数 0 → 0，现金不变）。

方向还不一致：

- 结余**为正**时这是**罚**（白丢一年收入）
- 结余**为负**时这是**赏**（白免一年支出）
- 而「被裁员 → 休养 2 回合」恰好落在后者 —— **等于把失业惩罚抵掉了一部分**

> 待决策：暂停是否应该照常结算。若照常，需要为暂停回合补一条「入不敷出」的弹层路径
> （暂停的玩家仍需要处理资金缺口，只是不能投资/求职）。

### 5.2 ⚠️ 出圈后结算频率突增 5.33 倍

| | 发薪/分红日个数 | 每轮移动 | 每轮结算次数 |
|---|---|---|---|
| 内圈 | 3 / 24 | 3.5 格（1 粒骰） | **0.438** |
| 外圈 | 8 / 24 | 7.0 格（2 粒骰） | **2.333** |

「外圈 8 个分红日」×「2 粒骰子」两个因素叠加，让出圈后的年度结算密度变成内圈的 **5.33 倍**。
这不是设计意图，而是棋盘构成与骰子数各自演化的副产品。

### 5.3 ⚠️ 一回合最多可结算 3 年（外圈 8 年），而年龄只 +1

> **后续更新**：方案 A 落地后本条已不再成立 —— 「一年只结一次账」，
> 同一回合内即使经过多个结算格，也只有第一个真正结算（其余记为「因本年已结而略过」）。

穷举全部起止位置的结果：

| 情形 | 单回合最多经过 |
|---|---|
| 内圈 · 1 粒骰（≤6 步） | 2 个发薪日 |
| 内圈 · 3 粒骰（银翅膀，≤18 步） | **3 个发薪日** |
| 外圈 · 2 粒骰（≥2 步） | **8 个分红日** |

这是 §4 那个「两个时钟」问题最直观的形态。

### 5.4 ⚠️ 同局不同玩家的结算年数不同（同龄不同命）

4 人局实测（同一种子）：

```
甲: 移动 45 次 / 结算 17 年 | 乙: 43 次 / 21 年 | 丙: 45 次 / 21 年 | 丁: 39 次 / 18 年
→ 最大差 4 年
```

年龄同步推进，但账目各走各的。这是「结算由落格抽签决定」的必然结果。

### 5.5 ⚠️ 一回合内两次结算的金额可能不同

前一次 `amortize` 若恰好还清某笔贷款，月供会立刻从支出中消失。实测：

```
两次结算的月结余：¥1,029 → ¥1,729（第 1 次还清了房贷）
入账合计 ¥33,096 = annual(1029) + annual(1729)   ← 不是「单年 × 2」
```

这是**正确的行为**（第 2 年确实少了一笔月供），但要求弹层显示的是**合计**而不是单年的值 —— 本次已修（§6.2）。

### 5.6 ⚠️ 骰子上限与环长的耦合

3 粒骰子上限 18 步 < 环长 24，所以**一回合不可能绕满整圈**，同一格不会被重复经过。
但若将来把骰子上限提到 24 步（4 粒骰），就会绕满整圈、同一发薪日被结算两次：
`pathBetween` 的 guard 是 60、`movePlayer` 没有去重保护，届时必须先改这两处。

### 5.7 ⚠️ 无限模式的表观年龄

无限模式下 `isAgeMode(g) === false`，不会触发 65 岁退休结算，但 `ageOf` 仍按 `round` 增长
（`round = 80` → 99 岁）。界面已用 `isAgeMode` 屏蔽了年龄显示（只显示轮次），不会露出；
但 `refreshLife` 仍按年龄取曲线，因 `SALARY_CURVE` / `LIFE_STAGES` 末档是 `to:200`，
66 岁之后收入与支出结构会永久停在「职场后期」档。属可接受的建模截断。

## 六、本次修复

### 6.1 弹层金额与实扣不符（真 bug）

**修前**：`resolveSpace` 的发薪日分支写的是

```js
msg:`已领取月现金流 ${money(isFT?ftMonthly(p):finance(p).cashflow)}。`
```

`finance(p).cashflow` 是**月度值**，而 `movePlayer` 实际入账的是 `annual(...)`（年度值）。
实测同一回合：**弹层写 ¥674，实际到账 ¥8,088** —— 相差 12 倍，属典型的账实不符。

**修后**：`movePlayer` 把本回合的结算明细（`{ count, amount, deficit, years[] }`）挂在
`landed.settled` 上，`resolveSpace` 读它来组织文案。**显示与实扣同源，不可能再对不上。**
摘要一路穿过「入不敷出」流程，重入时不会丢。

### 6.2 多次结算被掩盖

**修前**：一回合经过 2 个发薪日时，弹层仍只说「已领取月现金流 X」——次数与总额都看不出来。
**修后**：`本回合经过 2 个发薪日，共结算 2 年：入账 ¥22,512。`

### 6.3 棋盘副标题过时

内圈发薪日格的 `sub` 从 `'领取月现金流'` 改为 `'结算一整年'`（上一轮把结算改成年度后漏掉的一处）。

## 七、发薪提示（经过结算格时的即时反馈）

### 7.1 触发条件

**只在「经过结算格但未停留」时出现**，判定集中在 `Engine.paydayNoticeOf(g, landed, inFT)`
（纯数据、零 DOM），界面（`UiCore.paydayNotice`）只负责渲染。

| 情形 | 是否提示 | 由谁通知 |
|---|---|---|
| 经过发薪日 / 分红日，落在别的格，且**有金额进账** | ✅ 本提示 | 本节所述 Toast |
| **停在**发薪日 / 分红日格 | ❌ | `resolveSpace` 的确认面板（结算年数 / 金额 / 略过次数） |
| 经过结算格但**纯入不敷出**（`deficit > 0` 且 `amount ≤ 0`） | ❌ | 入不敷出面板（`resolveSpace` 优先弹出） |
| 经过结算格但**本年已结**（`yearsPaid === 0`） | ✅ 文案不同 | 本提示，明说「已结过」 |
| 未经过结算格 | ❌ | —— |

**三种通知方式互斥且穷尽**：一个「有年份进账的结算回合」一定被其中恰好一种覆盖 ——
不会被说两遍，也不会一次都不说。回归里有一条断言直接核对这个等式。

实测覆盖比（单人 101 · 软件工程师 · 种子 20260920）：一生 18 个结算回合中，
**10 个（56%）靠本提示覆盖**、8 个停在结算格由确认面板覆盖。也就是说，
改动前有一半以上的发薪在界面上是「静默」的 —— 玩家只看到现金变多。

> ⚠️ 「本年已结」这一分支在正常流程里唯一可达的入口是**刚退休**：
> `retireBreakOf` 会把 `settledAge` 推到当年，此后同岁再经过发薪日全部略过。
> 若不提示，玩家会看到「踩到发薪日却什么都没发生」。

### 7.2 展示内容

数据全部来自 `landed.settled` —— **与实扣同源**，界面不自己算金额
（旧版就是因为弹层自己算了一遍月度值，出现过「弹层写 ¥674、到账 ¥8,088」）。

```
💰 已发薪 ¥26,280                    ← 主行：发生了什么 + 金额
结算 20 岁这一年                     ← 次行：这一次结的是哪几年
```

次行按情况叠加，最多三条：

| 情况 | 次行内容 |
|---|---|
| 跨多年一次结清 | `自 42 岁以来 4 年一次结清` |
| 一回合经过多个结算格 | `本回合经过 4 个分红日，3 个因本年已结而略过` |
| 同一次移动里正负都有 | `另有 ¥X 入不敷出，需另行补上` |

「本年已结」用**同一套两行结构**，但不带金额、用中性色：

```
💰 经过发薪日
61 岁这一年的账已结过，本次不再重复发薪
```

### 7.3 呈现形式

- **顶部 Toast**（`top: calc(56px + 12px)`，即顶栏正下方），**刻意不用弹层**：
  经过结算格是常态（内圈每轮约 0.438 次），每次都要求点一次「确定」会变成纯粹的点击负担。
- `z-index: 80`，高于弹层（61）—— 停在别的格时落格弹层会同时打开，提示必须在其之上可见。
- 有金额时用绿色（`--ok`）；同时有缺口时转红（`--err`）；「本年已结」用中性色。
- 2.4 秒后自动向上收回（与既有 Toast 共用同一套进出场动效），同屏最多 3 条。
- `pointer-events: none`，**永远不会挡住「掷骰子 / 结束回合」**。
- **永久记录在日志里** —— 提示是「当时看到了」，日志是「回头查得到」。

### 7.4 与发薪 / 时间推进的衔接

提示读的是 `movePlayer` 的返回值，触发点在「移动之后、落格事件之前」：

```
movePlayer      结算（现金入账 + 摊还负债 + settledAge 前移）→ 返回 landed
      ↓
finishRoll      U.paydayNotice(paydayNoticeOf(g, landed, p.inFT))   ← 提示在此触发
      ↓
resolveSpace    落格事件（弹层）
```

所以提示出现时，**钱已经到账、账已经结清** —— 它是对既成事实的「回执」，不是预告。
回归里同时钉住了两件事：`p.settledAge === ageOf(g)`（账目与时间同步前移）
与「现金实增 === 提示金额」（同源）。

> ⚠️ 提示**不参与任何结算**，也不改动 `settledAge` / 现金 / 负债 —— 它只读数据、只渲染。
> 把提示做成结算的副作用（例如在 `movePlayer` 里改字段）会让引擎依赖界面，
> 破坏「引擎零 DOM 依赖、可在 Node 里直接跑长局」这条既有约定。

单回合多结算的金额合计、穷举 432 种走法的路径完整性、年龄推进时机（移动中恒不变）、
入不敷出路径的摘要保全、出圈后分红日同口径、还清贷款那一年的金额变化、
同局各玩家结算次数差异、暂停回合行为、无限模式年龄、
**发薪提示的触发边界与「三种通知方式互斥且穷尽」**（第 ⑮ 节）。

**改动 `diceCount` / 棋盘格型分布 / `UNEMPLOYMENT` / `skipTurns` / `SOLO` 后必须重跑本脚本。**

浏览器侧另跑一次性探针（8 项，已删）：棋盘副标题、落格弹层金额与实扣一致、
一回合多结算的文案与合计、财务面板不混月度/年度口径。

## 九、「一个发薪日触发多次结算」的核查 —— 该说法不成立

### 9.1 现象与结论

玩家反馈：日志里出现「结算 2 年：入账 ¥26,592」「结算 3 年：入账 ¥28,512」两行，
看起来像**一次发薪触发了多次结算**；而且结算金额与面板上的「年结余」对不上。

**实测结论：不存在重复结算。** 那两行是**两笔不同回合**的结算，每一笔覆盖
「自上次结算以来经过的年数」——**「N 年」是一次结算覆盖的年数，不是结算次数**。

> 根因不是代码，是**文案歧义**：`结算 2 年` 里那个「2 年」，
> 读成「覆盖 2 年」也对、读成「结算了 2 次」也对，而后者是更自然的读法。

### 9.2 三条硬证据

**证据 1 —— 穷举 24 × 18 = 432 种走法**
单次移动中「真正结算」的发薪日格数最大值 = **1**。
同一次移动经过多个发薪日时，第 2 个起会在 `due <= 0` 分支被略过。

**证据 2 —— 拦截 `settledAge` 的每一次写入，核对一整局的区间**

| 指标 | 实测 |
|---|---|
| 结算次数 | 22 |
| 命中发薪日格 | 18 格 → 18 次结算（**每个发薪日恰好一次**）；另有 0 格因本年已结而略过 |
| 其中来自突变点（失业 / 退休 / 终局） | 4 次 |
| **结算区间重叠** | **0 对**（没有任何一年被结两次） |
| **未被结算的年龄** | **0 年**（20—65 岁共 46 年全覆盖） |
| **被结算两次的年龄** | **0 年** |
| 静默跳年（推走 `settledAge` 却没结算） | 0 次 |
| 入账金额 === 现金实际增加 | 18 / 18 笔一致 |

**证据 3 —— 截图里的数字自己能对上**

```
结算 2 年 = ¥26,592           → 每年 ¥13,296
紧随其后的日志：增加一个孩子（每月支出 +¥70） → 年支出 +¥840
¥13,296 − ¥840 = ¥12,456      → 正好等于面板上的「年结余 ¥12,456」
```

说明：结算用的是**加孩子之前**的结余（正确，因为那是结算发生时的真实结余），
面板用的是**加孩子之后**的结余（也正确）；两者不矛盾，差额恰好等于孩子带来的支出增量。
**一个重复计数的系统不可能算出这么严丝合缝的数。**

### 9.3 每个发薪日应有的行为（口径）

| 项 | 口径 |
|---|---|
| **结算次数** | **恰好 1 次**。同一次移动经过多个发薪日时，只有第 1 个真正结算 |
| **结算年数** | 自上次结算以来经过的年数 = `当前年龄 − 上次结算年龄` |
| **入账金额** | **年结余 × 结算年数**（年结余 = 月现金流 × 12） |
| **摊还本金** | 结算年数 × 12 期（领几年就还几年，两者必须同步） |
| **年龄** | **不由发薪日推进** —— 年龄由「整圈走完」推进（一轮 = 一年） |

「两次发薪日之间隔了几年，那一次就一次结清几年」是**方案 A** 的设计：
若每次固定只结 1 年，一生 45 年只结得到约 20 年（覆盖率 44.4%），两个时钟永远对不上。
详见 [`方案A与价格标定.md`](方案A与价格标定.md)。

### 9.4 代码位置：四个结算入口，四个守卫

| 位置 | 作用 |
|---|---|
| `engine.js` → `movePlayer()` | **唯一的落格结算点**。`due = ageNow − p.settledAge`；`due <= 0` → 记为「本年已结」并 `return` |
| `engine.js` → `settleAtBreak()` | 失业 / 退休突变点结算（在收入口径切换**之前**结清） |
| `engine.js` → `finalSettle()` | 终局结清（61→65 岁的养老金入账） |
| `engine.js` → `retireBreakOf()` | 仅单人：进入退休年龄时先按在职口径结清 |

**四个入口都有一句 `due <= 0 → return`。** 这就是「不会重复结算」的全部保证 ——
它把「已经结过的年份」自然变成一个空区间，而不是靠调用方自觉只调一次。

### 9.5 修复思路：代码不用改，改的是文案

**结论：引擎逻辑正确，无需修改。** 要修的是「让人误读」的措辞。
本轮改了五处，共同做法是 **「一次结算」+ 覆盖的年龄区间 + 算式**：

| 位置 | 旧 | 新 |
|---|---|---|
| `engine.js` 发薪日志 | `经过发薪日，结算 2 年：入账 ¥26,592` | `经过发薪日：一次结算（覆盖 21—22 岁共 2 年），入账 ¥26,592 = 年结余 ¥13,296 × 2` |
| `engine.js` 落格面板 | `自 35 岁以来经过的 2 年一次结清：入账 ¥…` | `一次结算，覆盖 21—22 岁共 2 年：入账 ¥… = 年结余 ¥… × 2。` |
| `ui-core.js` 顶部提示 | `自 35 岁以来 2 年一次结清` | `一次结算 · 覆盖 21—22 岁共 2 年 · 年结余 ¥13,296 × 2` |
| `engine.js` 突变点 / 终局 | `结算 4 年：入账 ¥…` | `收入变更前一次结清（覆盖 21—25 岁共 5 年），入账 ¥… = 年结余 ¥… × 5` |
| `ui-game.js` 规则页 | `结算一整年 … 一次发薪日 = 一年`（**与方案 A 矛盾**） | `一次结算结清「自上次结算以来经过的年份」… 每个发薪日恰好结算一次` |

**加上算式是关键**：`¥13,296 × 2 = ¥26,592` 摆在那里，玩家能自己核对，
不必猜「是不是重复结算了」。顺带也解释了「为什么结算金额不等于当前年结余」——
结余在两次结算之间会随年龄、贷款、子女变化。

> 规则页那条「一次发薪日 = 一年」是**方案 A 落地时漏改的**，与引擎实际行为矛盾，
> 本身也是造成误读的原因之一。**改文案时要顺手扫一遍别处的同义表述** ——
> 本次是靠截图才发现的（正则扫描漏了它，因为它用普通 `>` 而非 `&gt;`）。

### 9.6 如果你要的其实是「每个发薪日只结 1 年」

这是**方案 A 的反向选择**，代价必须说清：一生只有约 19 次发薪，
若每次固定结 1 年，则 45 年的人生只结算约 20 年（**覆盖率 44.4%**），
中后期会凭空缺掉一半收入 —— 这正是当初采用方案 A 要解决的问题。

要真正做到「一个发薪日 = 一年」，必须同时解决「发薪次数不足」：
要么把内圈发薪日从 3 个加到 6—7 个（≈ 每轮一次，但要砍掉投资机会格），
要么改成「每轮自动结算一次年度收支」（则失去「踩到发薪日」的节奏感）。
两条都属**棋盘层改动**，需要先决策再动手。

### 9.7 回归

`test/payday-trigger.js` 新增第 ⑯ 节（**9 项**，总数 76 → **87**）：
区间零重叠 / 重复计数 0 年 / 全覆盖 / 无静默跳年 / 每个发薪日恰好一次 /
「年结余 × 年数」算式成立 / 日志点明「一次结算」并给出区间与算式 /
不再存在旧写法 `结算 N 年：入账`。

> 该节用**属性拦截器**（`Object.defineProperty` 拦截 `settledAge` 的写入）来覆盖**全部四个**结算入口 ——
> 审计第一版钩的是导出的 `E.settleAtBreak`，而 `startJobless` / `retireBreakOf` / `finalSettle`
> 调的都是模块内函数，钩不到，于是误报「突变点 0 笔」并把缺口算成了亏损。

浏览器侧另跑 10 项一次性探针（已删）：提示条点明「一次结算」、给出区间与算式、
位于顶栏下方、不横向溢出、不遮挡主操作按钮。

> ⚠️ 改动结算文案、或新增任何结算入口后，**必须重跑第 ⑯ 节** ——
> 它守的是「不重复、不遗漏、不跳年」三件事。
