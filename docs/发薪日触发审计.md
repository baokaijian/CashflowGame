# 发薪日触发逻辑审计

> 审计对象：内圈「发薪日」与财务自由圈「分红日」的触发条件、重复/遗漏、年龄推进时机。
> 审计方式：枚举全部起止位置穷举 + 固定种子长局回归 + 浏览器端到端。
> 可复跑：`node test/payday-trigger.js`（53 项断言，退出码 0 = 全通过）。

---

## 一、结论速览

| 审计项 | 结论 | 依据 |
|---|---|---|
| **到达**发薪日是否触发 | ✅ 正确 | 路径末元素恒等于落点（穷举 24×18 = 432 种走法验证） |
| **经过**发薪日是否触发 | ✅ 正确 | 长局中「仅经过」触发 11 次，全部入账 |
| 是否**重复**结算 | ✅ 无重复 | 落格实测现金只增加一次；结算只在 `movePlayer` 内做一次，`resolveSpace` 只弹提示 |
| 是否**遗漏**结算 | ⚠️ 有一条：**暂停回合整年不结算** | 见 §5.1，属待决策项 |
| **年龄递增时机** | ✅ 时机正确（在 `endTurn → nextPlayer`，移动过程中恒不变） | 45 轮推进 45 次，移动中越界 0 次 |
| **年龄与发薪是否同步** | ❌ **不同步**（核心问题） | 一生 45 年只结算 20 年，覆盖率 44.4%；见 §4 |
| 弹层金额与实扣是否一致 | ❌ 修前不一致（已修） | 修前弹层写月度 ¥674、实发年度 ¥8,088；见 §6 |

## 二、触发条件：到达 vs 经过

### 2.1 代码依据

```js
function pathBetween(from, to){        // engine.js
  const out = []; let i = from;
  do{ i = (i+1) % RING_LEN; out.push(i); } while(i !== to && guard < 60);
  return out;                          // ← 末元素就是落点
}
```

`pathBetween` 生成的是**半开区间 `(from, to]`**：包含落点、不含起点。
`movePlayer` 对 `path` 整体遍历，逐格判断格型，因此

- **落在发薪日上** → 落点被包含在路径里 → 触发 ✅
- **只是经过** → 中间格被包含在路径里 → 触发 ✅

两种情形共用同一段代码，不存在「只处理其中一种」的分支。穷举验证：
24 × 18 = **432 种走法中，路径末元素全部等于落点**，无一例外。

### 2.2 实测（单人 101 · 种子 20260920 · 45 轮）

```
45 次移动，路径命中发薪日 20 次
  其中【到达】触发 8 次、【仅经过】触发 11 次、一次经过多个 1 次
```

> 8 + 11 = 19 个「有命中的回合」，而命中总数是 20 —— 差的 1 次来自那个「一回合经过 2 个发薪日」的回合。两个数字都能对上，没有第四种情况。

## 三、是否重复 / 是否遗漏

### 3.1 不重复 ✅

`movePlayer` 只做结算，`resolveSpace` 对发薪日格**只弹提示、不再入账**。实测：

| 检查 | 结果 |
|---|---|
| 落在发薪日的现金变化 | `¥25,080`，与引擎 `collected` 完全一致（不翻倍） |
| 该回合摊还期数 | 4 笔在贷负债**每笔**各 +12 期（一年），无一笔被重复摊还 |
| 落格弹层类型 | `info`（纯提示），不产生第二次入账 |

### 3.2 不遗漏 ✅（除暂停回合，见 §5.1）

- 长局 45 次移动中「路径命中数 === 结算记录数」（20 vs 20），不一致 0 次
- 遍历全部 `pending` 分支（入不敷出 / 机会 / 慈善 / 意外支出 / 失业 / 休假…）后仍成立
- **入不敷出路径不丢信息**：结算摘要挂在 `landed.settled` 上，一路穿过「入不敷出」面板并在补款后重新落格时仍存在

> 这一条是上一轮埋下的隐患：`landed` 在入不敷出流程里被 `Object.assign({}, landed, {deficit:0})` 复制，
> 若摘要挂在别处（如球员对象或全局）就会在重入时丢失，弹层会显示 ¥0。

## 四、年龄递增时机（核心问题）

### 4.1 现状

```js
function ageOf(g){ return g.startAge + (g.round - 1); }        // 年龄 = 20 + 轮次 − 1
function nextPlayer(g){
  if(g.cur === 0){ trackRound(g); g.round++; refreshAllLife(g); ... }   // ← 整圈走完才 +1
}
```

**年龄的推进时机是正确的**（实测 45 轮推进 45 次；移动与发薪结算过程中年龄越界 0 次）。
问题不在时机，而在**它和发薪日是两个互不相干的时钟**：

| 时钟 | 由什么驱动 | 频率 | 覆盖 |
|---|---|---|---|
| **年龄时钟** | 整圈走完（`g.round`） | 每轮 1 次 | 45 轮 = 45 年 ✅ |
| **金钱时钟** | 落在/经过发薪日 | 内圈每轮 **0.438** 次 | 一生 45 年只结算 **20 年** ❌ |

内圈 24 格只有 3 个发薪日（位置 2/7/14），而每轮平均只走 3.5 格 ——
平均要 **6.9 轮才走完一圈**，一生 45 轮只能绕 6.5 圈。实测结果：

```
一生 45 年：年龄推进 45 次、发薪结算 19 次（合计 20 年）
→ 结算覆盖率 44.4%
发薪时刻的年龄：21, 24, 28, 30, 31, 34, 35, 37, 39, 40, 44, 47, 48, 51, 54, 57, 59, 62, 64
→ 两次结算之间平均间隔 2.25 年
```

### 4.2 为什么不能「让发薪日推进年龄」

这是这次要求的核心诉求，但**不能这么做**，原因有数：

1. 一生只有约 **19—20 次**发薪（上表）。若由它推进年龄，45 轮结束时角色只有 **39 岁**，
   「65 岁退休结算」这个胜负条件会立刻失效。
2. 要把发薪次数提到 45 次，内圈需要约 **7 个发薪日（29% 的格子）** ——
   棋盘只能从 8 个投资机会格里去砍，等于把核心玩法砍掉一半。
3. 更糟的是**激励会反过来**：谁更常踩到发薪日谁老得更快，
   于是「躲开发薪日」变成最优策略 —— 与实际直觉完全相反。

**结论：年龄时钟必须由「一轮 = 一年」独占。** 要消除两套时钟，只能让**金钱时钟去跟随年龄时钟**。

### 4.3 两条彻底对齐的路径（待决策）

| 方案 | 做法 | 一生累计结算 | 代价 |
|---|---|---|---|
| **A（推荐）** | 发薪日结算「自上次结算以来经过的年数」，而不是固定 1 年 | 45 年 | 单次金额变成 1—4 年不等；总收入约 **×2.25** |
| **B** | 每轮边界自动结算一年，发薪日改为一次性奖励 | 45 年 | 失去「踩到发薪日」的节奏感；棋盘上 3 个发薪日格失去意义 |

两方案的共同影响：**出圈条件（被动收入 > 总支出）是比率条件，不受影响**；
但累计现金会变成 2.25 倍，而资产价格是绝对值 —— 所以**中后期的购买力会明显上升，需要重新做一轮价格标定**。
在价格标定之前贸然切换会让游戏变得过于宽松，因此本次**未实施**，等决策。

## 五、边界情况与逻辑缺陷清单

### 5.1 ⚠️ 暂停回合：时间在走、账不走

失业休养与健康危机的 `skipTurns` 回合，玩家**不移动 → 不结算收入、也不摊还负债**，
但年龄照常 +1（实测：期数 0 → 0，现金不变）。

方向还不一致：

- 结余**为正**时这是**罚**（白丢一年收入）
- 结余**为负**时这是**赏**（白免一年支出）
- 而「被裁员 → 休养 2 回合」恰好落在后者 —— **等于把失业惩罚抵掉了一部分**

> 待决策：暂停是否应该照常结算。若照常，需要为暂停回合补一条「入不敷出」的弹层路径
> （暂停的玩家仍需要处理资金缺口，只是不能投资/求职）。

### 5.2 ⚠️ 出圈后结算频率突增 5.33 倍

| | 发薪/分红日个数 | 每轮移动 | 每轮结算次数 |
|---|---|---|---|
| 内圈 | 3 / 24 | 3.5 格（1 粒骰） | **0.438** |
| 外圈 | 8 / 24 | 7.0 格（2 粒骰） | **2.333** |

「外圈 8 个分红日」×「2 粒骰子」两个因素叠加，让出圈后的年度结算密度变成内圈的 **5.33 倍**。
这不是设计意图，而是棋盘构成与骰子数各自演化的副产品。

### 5.3 ⚠️ 一回合最多可结算 3 年（外圈 8 年），而年龄只 +1

穷举全部起止位置的结果：

| 情形 | 单回合最多经过 |
|---|---|
| 内圈 · 1 粒骰（≤6 步） | 2 个发薪日 |
| 内圈 · 3 粒骰（银翅膀，≤18 步） | **3 个发薪日** |
| 外圈 · 2 粒骰（≥2 步） | **8 个分红日** |

这是 §4 那个「两个时钟」问题最直观的形态。

### 5.4 ⚠️ 同局不同玩家的结算年数不同（同龄不同命）

4 人局实测（同一种子）：

```
甲: 移动 45 次 / 结算 17 年 | 乙: 43 次 / 21 年 | 丙: 45 次 / 21 年 | 丁: 39 次 / 18 年
→ 最大差 4 年
```

年龄同步推进，但账目各走各的。这是「结算由落格抽签决定」的必然结果。

### 5.5 ⚠️ 一回合内两次结算的金额可能不同

前一次 `amortize` 若恰好还清某笔贷款，月供会立刻从支出中消失。实测：

```
两次结算的月结余：¥1,029 → ¥1,729（第 1 次还清了房贷）
入账合计 ¥33,096 = annual(1029) + annual(1729)   ← 不是「单年 × 2」
```

这是**正确的行为**（第 2 年确实少了一笔月供），但要求弹层显示的是**合计**而不是单年的值 —— 本次已修（§6.2）。

### 5.6 ⚠️ 骰子上限与环长的耦合

3 粒骰子上限 18 步 < 环长 24，所以**一回合不可能绕满整圈**，同一格不会被重复经过。
但若将来把骰子上限提到 24 步（4 粒骰），就会绕满整圈、同一发薪日被结算两次：
`pathBetween` 的 guard 是 60、`movePlayer` 没有去重保护，届时必须先改这两处。

### 5.7 ⚠️ 无限模式的表观年龄

无限模式下 `isAgeMode(g) === false`，不会触发 65 岁退休结算，但 `ageOf` 仍按 `round` 增长
（`round = 80` → 99 岁）。界面已用 `isAgeMode` 屏蔽了年龄显示（只显示轮次），不会露出；
但 `refreshLife` 仍按年龄取曲线，因 `SALARY_CURVE` / `LIFE_STAGES` 末档是 `to:200`，
66 岁之后收入与支出结构会永久停在「职场后期」档。属可接受的建模截断。

## 六、本次修复

### 6.1 弹层金额与实扣不符（真 bug）

**修前**：`resolveSpace` 的发薪日分支写的是

```js
msg:`已领取月现金流 ${money(isFT?ftMonthly(p):finance(p).cashflow)}。`
```

`finance(p).cashflow` 是**月度值**，而 `movePlayer` 实际入账的是 `annual(...)`（年度值）。
实测同一回合：**弹层写 ¥674，实际到账 ¥8,088** —— 相差 12 倍，属典型的账实不符。

**修后**：`movePlayer` 把本回合的结算明细（`{ count, amount, deficit, years[] }`）挂在
`landed.settled` 上，`resolveSpace` 读它来组织文案。**显示与实扣同源，不可能再对不上。**
摘要一路穿过「入不敷出」流程，重入时不会丢。

### 6.2 多次结算被掩盖

**修前**：一回合经过 2 个发薪日时，弹层仍只说「已领取月现金流 X」——次数与总额都看不出来。
**修后**：`本回合经过 2 个发薪日，共结算 2 年：入账 ¥22,512。`

### 6.3 棋盘副标题过时

内圈发薪日格的 `sub` 从 `'领取月现金流'` 改为 `'结算一整年'`（上一轮把结算改成年度后漏掉的一处）。
