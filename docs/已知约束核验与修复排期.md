核验日期：2026-09-26。代码基线：`27a50ad`。范围为 README 的“已知约束”及其引用的存档限制。

状态：**第一批 D1—D3 已实施；D1 历史来源不清的旧债仍需核对，D2 不猜测重建历史成交成本；D4—D6 尚未实施。** 排期以开始实施当天为第 1 个工作日，按单人连续开发估算，不是自动执行的后台任务或已承诺的上线日期。

## 一、结论与优先级

初次核验时 README 中列出的三处缺陷都存在；D1—D3 已在后续实施中修复，以下保留当时的证据。另确认自由圈在出售原资产后仍发放原分红，存档失败没有反馈，固定种子状态无法跨存档恢复。前两者需要从“简化 / 平台限制”提升为实际修复项。

- **P1：优先修复**，影响资金、净资产、收益归属或进度保存。
- **P2：随后修复**，影响显示一致性、续局可复现性或规则解释。
- **待评估 / 功能增强**：有边界不代表计算错误，不直接改成更复杂的现实模型。

没有因本次核验而宣布所有其他路径无缺陷；也没有将高报价直接判为必然失衡。

## 二、已确认问题与复现证据

### D1 · 初始房产组合重复计债（P1，已实施）

完成情况：新局只记录房产项目融资，租金使用扣息后的净额；可识别旧档迁移剩余本金，并覆盖已结清、转让、售出和买回。混合债务或凭据缺失时保留原账并显示待核对提示，不猜测核销。价格重算工具同步修复。详见 [D1 实施说明](资产报价与交易结算.md#d1-初始出租房组合融资修复)。

以下为修复前的复现证据：

入口：202 的“老破小出租房”初始组合。使用 `Engine.newGame({rule:'202',mode:'solo',count:1,seed:20})` 可得到该组合。

| 项目 | 实际结果 |
|---|---:|
| 房产取得成本 / 首付 | ¥170,000 / ¥50,000 |
| `liabs.other` | ¥120,000 |
| 同一房产 `projectDebt` | ¥120,000 |
| 执行一次年度 `amortize` 后的其他负债 | ¥119,855 |
| 同期项目融资余额 | 仍为 ¥120,000 |

`applyPortfolio` 登记其他负债，`registerProperty` 又从总价减首付推导项目融资；账面净资产和参考净资产都扣除两者。摊还只改变其他负债，因此不仅开局重复扣债，后续还本和售房也不能正确对应。

证据：[组合卡](../js/data-board.js) 的 `PORTFOLIOS`；[引擎](../js/engine.js) 的 `applyPortfolio`、`registerProperty`、`netWorth`、`valuedNetWorth`、`amortize`。

实施结果：融资只保留在房产，未来持有期付息、出售时还本。新局租金 ¥708 减利息 ¥492 后净现金流为 ¥216，原“其他负债”及其月供不再重复出现；起始现金和初始月结余不因换口径改变。旧档已还本金保留，不再按最初 ¥120,000 重建余额。

旧档重点：已有还款、追加其他借款或已卖房的存档不能一律减掉 ¥120,000。现按组合来源、贷款计划、产权及售房凭据匹配；不能拆分的旧债保留原账并提示，也不回算历史现金。

### D2 · 协议转让未重建买方成本（P1，已实施）

完成情况：股票 / 企业转让已统一到 `Act.transferAsset`，以持仓编号校验，按成交总款建立买方成本、生成新编号并记录交易。股票单位成本保留小数；企业累计使用年数与经营参数继续保留，买方取得时间单独登记。不对缺失成交凭据的历史交易猜测补账。以下为修复前证据：

执行当前 `sellAssetDialog` 的真实点击回调，分别转让股票和企业：

| 场景 | 成交现金 | 买方实际记录的成本 | 应记录成本 |
|---|---:|---:|---:|
| 100 股，卖方单价成本 ¥10 | ¥3,000 | 单价 ¥10，总额 ¥1,000 | 单价 ¥30，总额 ¥3,000 |
| 卖方成本 ¥1,000 的企业 | ¥3,000 | ¥1,000 | ¥3,000 |

现金支付正确，但资产对象直接从卖方数组移入买方数组。成本没有改变，企业报价若以成本为基准，也会继承不正确的基数。

证据：[玩家交易](../js/ui-game.js) 的 `sellAssetDialog`。房产走 `Act.transferProperty`，已有独立成本处理，不应倒退为这条旧路径。

实施结果：金额、参与玩家、资金和持仓有效性先校验再改账；重复提交和旧行情选项不会操作新持仓。协议价不改写股票的共享行情，买方同股持仓暂保留为不同批次。非整数单位成本不取整，界面同时显示总成本和小数单价。

### D3 · 门槛和部分规则文案不一致（P2，已实施）

完成情况：财务面板和玩家详情均显式传入当前规则，门槛读取 `escapeTarget`；帮助、复盘和破产日志的旧文案已清理。以下为修复前证据：

对同一测试职业渲染收入表：

| 规则 | 表中显示的年门槛 | 引擎实际年门槛 |
|---|---:|---:|
| 101 | ¥67,188 | ¥100,788（×1.5） |
| 202 | ¥67,188 | ¥167,976（×2.5） |

收入表底部把总支出当作门槛；规则页仍有“门槛本身就是总支出”。破产日志也仍显示出局后“跳过 3 回合”的旧规则。这些不改变当前判定，但会误导玩家。

证据：[财务与规则界面](../js/ui-core.js) 的 `renderIncomeBase`、规则文案；[引擎](../js/engine.js) 的 `escapeTarget` 及破产日志。

实施结果：显示与判定同源，明确“严格超过”；还款说明保留生活预算下限；破产说明统一为退出本局。复盘界面与 Markdown 导出说明保留记录及采样点的截断边界，不再承诺完整流水。

### D4 · 出圈后卖出资产仍保留原分红（P1）

构造唯一一套有现金流的房产，实际调用 `escapeRatRace`，再通过 `marketOptions` / `marketSell` 售出：

| 项目 | 出售前 | 出售后 |
|---|---:|---:|
| 持有房产数量 | 1 | 0 |
| 普通账本被动收入 | ¥100,000/月 | ¥0/月 |
| 自由圈收入 | ¥100,000/月 | 仍为 ¥100,000/月 |

这里的 ¥100,000 是用于隔离问题、保证出圈的测试数据，不是卡片正常收益。问题在于原资产仍可出售，而基础分红永久锁定，导致现金变现后同一来源的收入继续存在。

证据：[动作](../js/engine-actions.js) 的 `escapeRatRace`、`marketSell`；[引擎](../js/engine.js) 的 `ftMonthly`、`ftFinance`；[玩家交易入口](../js/ui-game.js)。

修复方向：建议自由圈原资产收入随当前持仓和合同变化，继续保留既定出圈奖励及工资退出规则。覆盖市场出售、玩家转让、急售、租金行情、灾害和机构管理费等路径；自由圈企业不得重复计入。

旧档重点：原 `ftBase` 与现有持仓不能同时无条件叠加。应标明新旧规则版本，保留历史已发现金，只迁移未来收入，并解释可能的收入下降。如果产品最终选择保留固定分红，必须先将其定义为独立权益并处理原资产的退出，不能继续两边保留。

### D5 · 存档写入失败静默丢进度（P1）

向当前 `saveState` 注入会抛出配额异常的 `localStorage.setItem`：发生一次写入失败，异常被 `store` 吞掉，无失败状态或通知。玩家可能继续操作，刷新才发现进度未保存。

证据：[保存与恢复](../js/ui-game.js) 的 `store`、`saveState`、`scheduleSave`、`tryRestore`。合并写入与离页保存已经存在，不能描述成完全没有自动保存。

修复方向：保存成功时间 / 失败状态可见，失败不覆盖上一份有效记录，提供重试及完整存档备份。备份与复盘 JSON 明确区分；若增加恢复导入，须校验结构和版本，在临时状态完成迁移后再替换当前对局。无法让浏览器异常退出前的每一步都保证落盘，验收不作此承诺。

### D6 · 固定种子在恢复后失效（P2）

开局 `g.rng` 是闭包函数；序列化时被移除，恢复时显式设置为 `null`。牌堆已经抽出的顺序仍保存，但其随机函数同样不能被 JSON 保存，后续掷骰及重洗退回非种子随机源。

证据：[引擎](../js/engine.js) 的 `newGame`、`makeDeck`、`drawCard`、`rollDice`；[恢复逻辑](../js/ui-game.js) 的 `saveState`、`tryRestore`。

修复方向：随机源使用可序列化状态，所有随机入口共享并推进该状态；恢复同一存档后，给定同样操作应产生同样骰子、重洗和事件。旧档缺少随机历史无法准确恢复，只能建立此后的可保存状态，不能伪称延续原序列。

## 五、验收范围与本次实际验证

### 每批都要守住的边界

- 交易与借贷被拒时，现金、资产和负债不发生部分修改；重复提交不能重复付款。
- 同一笔融资只扣一次；产权份额、项目余额、成本、估值、出售净款相互可核对。
- 每经过一个结算日只结算一年并长一岁；不能因修复收入来源而再发一遍钱。
- 同一笔收入或机构费不重复计入；出圈后已有生活预算继续生效。
- 旧档迁移可重复执行，不重放已发生的现金收支；不能识别的历史有明确说明。
- 代码修改后更新资源版本，运行对应 Node 回归及受影响的浏览器交互；最后一批运行全部 Node 验证和浏览器行为探针，逐批同步 README 状态。
