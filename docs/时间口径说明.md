# 时间口径说明（第一步）

> **一句话**：本作的时间主轴是 **一轮 = 一年**；金融侧按**年度**结算 ——
> 每结算一年，领到的是 12 个月的结余、还的是 12 期本金，
> 负债的剩余期限以**年**呈现。所有金额口径只有一个真源：`window.TIME`（`js/data-careers.js`）。
>
> ⚠️ **本文记录的是第一步**：把「一次结算 = 一个月」统一成「按年结算」。
> 它当时写的「一次发薪日 = 一年」是**简写，且不准确** ——
> 落地后发现落格触发频率只有每轮约 0.44 次，若每次固定只结 1 年，
> 一生 45 年只能结到约 20 年（覆盖率 44.4%）。
> 后续两步：**第二步（方案 A，已回滚）**改为「一次结算结清自上次结算以来经过的年数」，
> 见 [`方案A与价格标定.md`](方案A与价格标定.md)；
> **第三步（现行定稿）**回归「一个发薪日 = 结算 1 年」，靠**积欠模型**（没踩到发薪日的
> 年份记在 `settledAge` 落后量里，由突变点 / 终局一次结清）保证不丢年，
> 见 [`结算步长与发薪日密度.md`](结算步长与发薪日密度.md)。
> 阅读本文时请把「一次发薪日 = 一年」理解为「**一个结算年 = 12 个月**」。

---

## 一、改之前存在的三处不一致

这三处不是同一个问题，而是同一条时间轴上被切成了三段不同的刻度。

### ① 期限用「月」、游戏用「年」

改前负债模块显示 `剩余 140 期`。这个「期」是**月**（合同月供按日/月计息），
而游戏里一轮 = 一年 —— **两套刻度并排显示，玩家无法对照**。

更严重的是：45 轮里平均只经过约 **20 次发薪日**，而一次发薪日只摊还 **1 期**。
于是 140 期的房贷**一辈子还不完**（20/140 ≈ 14%），「剩余 140 期」这个数字
从开局到退休几乎不动。

### ② 收入按「月」、时间按「年」

改前一次发薪日领的是**一个月**的结余。45 年里只结算约 20 次，
相当于这个人**一生只工作了 20 个月**。实测（4 人局 101，会买入的 AI）：
期末现金只有 ¥6,006—18,243，被动收入 ¥0—300，而出圈门槛是 ¥2,041—3,504 ——
**被动收入根本够不着门槛，获胜条件形同虚设**。

### ③ 内圈按「月」、外圈按「月」但密度不同

财务自由圈的「分红日」是发薪日的对应物，但每圈有 **8 个**（内圈只有 3 个）。
两圈各按各的节奏结算，跨圈之后口径又变了一次。

## 二、统一后的口径

```
一轮 = 一年
一个结算年 = 12 个月  ← 唯一真源：window.TIME.monthsPerPayday
（⚠️ 它是一个结算年折算的月数，不是「每次落格只结 1 年」——
   一次结算覆盖的年数 = 自上次结算以来经过的年数，见方案 A）

结算时（按结算年数 N）：
  领到的钱 = 月结余 × 12 × N    （年收入 − 年支出）
  还的本金 = 12 × N 期          （逐期计息、逐期取整）
  剩余期限 = 剩余期数 ÷ 12 → 年  （向上取整）
```

数据文件里的金额**仍然按「月」记录**（职业卡的工资与月供、卡片上的月现金流），
这是原本就有的口径 —— 不改它，是为了避免同时存在两套数字。
引擎在发薪日把它们合并成年度结算，界面通过 `E.annual(v)` 统一换算。

| 层面 | 改前 | 改后 |
|---|---|---|
| 一轮 | 一年 | 一年（不变） |
| 一次发薪日 | 1 个月 | **1 年（12 期合并结算）** |
| 收支表 | 月度（月总收入 / 月现金流） | **年度（年总收入 / 年总支出 / 年结余）** |
| 负债期限 | `剩余 140 期` | **`剩余 12 年`** |
| 负债还款额 | `月供 ¥700` | **`年供 ¥8,400`** |
| 提前还款 | `缩短期限 / 减少月供` | `年供不变·缩短期限 / 期限不变·降低年供` |
| 自由圈分红日 | 领月度现金流 | **领年度分红** |
| 顶栏 / 席位卡 / 面板 | 三处各写各的 | 全部读 `E.annual()`，实测三处数字完全一致 |

**1200 / 140 / 12 这类数字不再出现在代码里**：`test/time-unit.js` 有一条断言
扫描 `engine.js`，禁止出现写死的 `× 12` —— 口径一旦写死在多处，改的时候必然漏掉一两处。

## 三、边界与处理

| 情形 | 处理 |
|---|---|
| **剩余期数 = 0**（余额已为 0） | 剩余年限 = 0，该笔贷款从负债表**整行消失**；年供归零、不再计入支出，年结余同步改善 |
| **剩余期数 ≤ 12**（不满一年） | 年限**向上取整**为 1 年 —— 显示「剩余 0 年」会让玩家以为已经还清。还清的那一刻余额即为 0，这一行直接消失，所以界面上**永远不会出现「剩余 0 年」** |
| **月供 ≤ 月利息**（永远还不完） | `periodsOf` 返回 `Infinity`，`toYears` **原样透传**（不会被误算成 0 年）。界面按「无法还清」呈现，提示玩家本金过大或月供过低 |
| **一年内还清**（余额不足 12 期） | 逐期循环遇到余额 ≤ 1 即提前退出，不会还出负数；多出来的那几个月不再计息 |
| **信用贷（随借随还）** | 没有固定期数，显示「随借随还 · 无固定期数」，不参与年限换算 |
| **同一次移动经过多个发薪日** | 每个发薪日各结算一年（走满 24 格 = 经过 3 个发薪日 = 摊还 3 年），不会合并成一次 |
| **入不敷出（年结余为负）** | 缺口 = 月缺口 × 12，走同一套资金不足面板；不会把现金扣成负数 |
| **「企业月现金流之和 ≥ ¥50,000」** | 这是**资产规模**的度量（所购企业每月现金流之和），与结算周期无关，**不随本次改动变化** |
| **出圈资金 = 月被动收入 × 100** | 原版的游戏化数字（≈ 8.3 年的被动收入），**不是按年结算的金额** —— 界面已把单位写明，避免与年度金额混读 |

## 四、平衡影响（必须知道）

这次改动让**时间口径自洽**，但它同时改变了货币供给 —— 因为游戏一共只发约 20 次薪，
而改后每次发的是一整年。实测对照（4 人局 · 101 规则 · 同一随机种子 · 会真实买入的 AI）：

| 指标 | 改前（1 次发薪日 = 1 月） | 改后（1 次发薪日 = 1 年） |
|---|---|---|
| 期末现金 | ¥6,006 — ¥18,243（均值 12,337） | ¥247,754 — ¥806,942（均值 481,401） |
| 第 25 轮负债 | ¥56,642 — ¥90,915 | ¥6,810 — ¥13,749 |
| 期末负债 | ¥53,221 — ¥86,899 | ¥2,154 — ¥2,798 |
| 被动收入 | ¥0 — ¥300 | ¥2,700 — ¥5,500 |
| 出圈门槛 | ¥2,041 — ¥3,504 | ¥1,416 — ¥2,534 |
| **能否达到出圈条件** | **否** | **是** |

两个方向相反的结论，都要说清楚：

- ❗ **货币规模膨胀约 12 倍**（现金均值 12,337 → 481,401，约 39 倍，差额来自「贷款提前还清」）。
  资产价格没有变，所以玩家在中后期会明显变宽裕。
- ✅ **但获胜条件第一次变得可达**。改前 AI 的被动收入（0—300）永远够不着门槛（2,041—3,504），
  「被动收入 > 总支出」这条核心规则实际上是不可完成的；改后被动收入（2,700—5,500）
  已经越过门槛（1,416—2,534）。

**换句话说：改前的经济模型无法支撑它自己的获胜条件。** 这次改动暴露的是
「收入侧被严重低估」这个更底层的问题，而不是单纯的单位标注问题。

### 若要让难度回到改前水平，有三个方向（尚未实施）

1. **把资产价格与卡片金额统一 ×12** —— 最彻底，但涉及四个数据文件里数百个数字，
   需要一轮专门的标定与回归（风险：漏改一处即出现两套刻度）。
2. **降低发薪日密度**（内圈 3 个 → 更少）—— 让「一年一次结算」在体感上更接近。
3. **抬高出圈门槛的倍数**（101 的 ×1 → 更高）—— 最小改动，但只是补偿结果，不解决根源。

## 五、⚠️ 仍然存在的不一致（本次未解决）

**这一条最重要，必须知道：**

> **年龄按「轮」推进（45 轮 = 45 年），发薪日按「格」触发（每轮约 0.44 次）。**

也就是说：**一生的 45 年里，只结算了约 20 年的收入。**
`test/time-unit.js` 会把这两个数字打印出来对照：

```
· 内圈 24 格 / 3 个发薪日 → 平均每轮 0.44 次
· 45 轮合计约 20 次发薪日 = 20 年（⚠️ 小于 45 年，见文档）
```

由此派生一个更荒谬的推论：**走得慢的人 = 人生更短**。
因为发薪日靠落格触发，掷骰运气差的玩家在同一段时间里少结算几次收入 ——
而按现在的口径，每一次结算都代表一整年。

**要彻底消除它，只有两条路**（都属于棋盘层改动，需要单独评估）：

- **A. 每轮自动结算一次年度收支**（不再依赖落在发薪日格上），
  发薪日格改为一次性奖励 → 45 轮 = 45 次结算 = 45 年，完全自洽。
  代价：棋盘失去「踩到发薪日」的节奏感。
- **B. 增加内圈的发薪日格到 6—7 个**（≈ 每轮 1 次）→ 保持落格机制且密度匹配。
  代价：24 格里近三成是发薪日，棋盘的格子类型分布需要重排。

在选定方案之前，当前口径是**「结算单位一致、但结算次数与年数不等」**的状态 ——
比改前（连单位都不一致）好，但仍不是一个完全自洽的时间模型。

## 六、参数与验证

| 参数 | 位置 | 值 |
|---|---|---|
| `TIME.monthsPerPayday` | `js/data-careers.js` | 12（一次发薪日结算的月数） |
| `TIME.monthsPerYear` | `js/data-careers.js` | 12（利率年化的分母，与上者概念不同） |
| `LOAN_TYPES.*.rate` | `js/data-careers.js` | **月**利率（合同口径，保持不变） |

引擎侧的换算只有一个入口：`E.monthsPerPayday()` / `E.monthsPerYear()` /
`E.annual(v)` / `E.toYears(期数)` / `E.toYearsFloor(期数)`。

```bash
node test/time-unit.js      # 37 项断言，退出码 0 = 全通过
```

覆盖：口径真源唯一、`engine.js` 里不得出现写死的 `× 12`、
剩余期数 → 年的换算（含 `Infinity` 与不满一年的边界）、
**一次发薪日恰好摊还 12 期且余额与年限同步下降**、
绕一圈经过 N 个发薪日就恰好摊还 N 年（不会多还）、
还清的边界（余额归零 / 年供归零 / 从支出消失 / 重复结算不出错）、
贷款确实能在整局内还清、**单人模式与多人模式同口径**、
长局中剩余年限随游戏推进**单调下降**（不回升）。

> 改动 `TIME`、`LOAN_TYPES`、或职业卡的负债数据后**必须重跑本脚本**。
